## [C] 23 findings - "briefing mentions a time after its decision minute"

Every hit was extracted with its JSON path and surrounding text and classified. **One was
real.**

### REAL - voided and re-run

| briefing | field | text |
|---|---|---|
| `A2_0954_manage.json` | `thesis_context.other_side_tripwire` | *"the orchestrator's mechanical scan resolves it at 09:56, two minutes after this call"* |

The 09:56 tripwire resolution is derived from bars **after** the 09:54 decision minute.
RUNBOOK 2b forbids telling an agent when a later event falls - forward information about
activity, even carrying no price. **The management call was voided, the briefing rebuilt
without the reference, and `tv-manage` re-run against the same (clean, leak-checked)
screenshot.** The clean re-run returned an identical decision - partial 75% at TP1 30566.00,
stop unchanged - so no trade result changed. That could only be established by re-running it.

Standing change: briefings never state when a scanned or scheduled event will occur. The
orchestrator holds the tripwire scan; agents are told only that a tripwire is armed.

afternoon or the Sunday/Monday evening reads as "after" a morning decision minute. All of

- `18:00` - the session open (Mon 2026-06-01 18:00), appearing in `session_calendar`,
  `higher_timeframe_at_candidate_levels.*.session_open`, and the weekly anchor.
- `18:02`, `18:04`, `18:18` - `context_extras.swept.*.swept_at`, sweeps in the first minutes
  after the 18:00 open.
- `20:56`, `21:02`, `21:22`, `21:32`, `22:32`, `22:52`, `23:20`, `23:34`, `23:56` -
  `context_extras.swept.*.set`, Sunday-evening swing points, each printed in the payload with
  its `Sun`/`Mon` prefix.
- `06:44`, `08:46`, `11:36`, `12:00`, `12:02`, `12:34`, `12:48`, `13:10`, `14:16`, `15:00`,
  `15:02`, `15:30`, `16:16`, `16:44` - the same field for **Monday** swing points, i.e. the
  prior cash session.

## [D] 1 finding - "corpus answer-key markers present: ['his_words']"

**Key name, not content - now renamed.** `data/reference/blackout_policy.json` used the key
`his_words` to hold his standing ruling that ISM Manufacturing PMI does not gate entries.
`his_words` is the key used inside `data/narrated_days/*.json`, so check D treats it as an
answer-key marker wherever it appears.

The content is standing policy the orchestrator is **required** to state in a macro briefing.
It records which calendar events gate entries and says nothing about what happened on any
replayed day. The key is now `ruling_quote`, with a note in the file explaining why.

The file flagged, `LONDON_0300_macro_brief.json`, was the path-based briefing from the first
macro attempt, which the agent never read - `tv-macro-events` carries no tools. The same
content did reach the agent inline on the successful call.
